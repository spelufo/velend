❯ This is a blender custom renderer that allows visualization of huge x-ray     
  scans stored as ome-zarr on disk inside blender, by texturing meshes by where 
  they slice the x-ray volume.                                                  
                                                                                
  What is working now is having two large 3d textures on the gpu that we load   
  the appropiate data to. The vesuvius.Volume data source is lazy loaded from   
  disk, in chunks.                                                              
                                                                                
  To make more efficient use of the limited memory, we want to change how we do 
  rendering: We will break each mesh's triangle along the planes dividing an    
  the cubes of an orthogonal grid in a geometry shader, and texture each with a 
  subcube of a 3d texture atlas corresponding to that chunk.                    
                                                                                
  We will stream subcubes of data into one large 3d texture until it is full.   
  We will have a focus point in 3d space to establish priority over which       
  chunks prevail in the gpu texture vs which get evicted when there isn't space 
  (closest chunk to the focus wins). Triangles that didn't get mapped because   
  there wasn't enough space can fall back to the downsampled 3d texture         
  (already implemented) that covers the whole space. All meshes share the same  
  large 1024^3 3d texture.                                                      
                                                                                
  To avoid seams, each subvolume in the 3d texture will have a little padding.  
  The size of the renderer's chunks doesn't necessarily match the size of the   
  chunks on disk (which is opaque to us).

  Geometry shaders are not available. gpu.types.GPUShaderCreateInfo exposes only
  vertex_source, fragment_source, and compute_source — there is no geometry
  stage in Blender's Python GPU API, and your Metal backend has no geometry
  stage at all. Also confirmed: GPUTexture has no sub-region upload
  (clear/read/format only), but gpu.compute.dispatch + shader_info.image(..., 
  qualifiers={'WRITE'}) do exist, which is how bricks can be streamed into a
  persistent atlas.

  Concrete numbers I pulled: L0 is 18977×6844×6844 uint8, uncompressed, 128³
  disk chunks; L5 is 594×214×214 (the 27 MB fallback texture you already have);

  Some things I can expand on if useful:

  - Why splitting is off the table mechanically — GPUShaderCreateInfo in your
    Blender 5.1.2 build exposes only vertex_source / fragment_source /
    compute_source; I confirmed this by introspecting the actual binary, not
    from docs.
  - Whether the page-table approach really gives the same result — it does: each
    fragment is textured from its own chunk's padded subcube with hardware
    trilinear filtering. The difference is only where the chunk lookup happens
    (per fragment vs. per triangle), not what gets sampled.
  - The cost of the per-fragment lookup — one extra texelFetch on a small R16UI
    3D texture (~7 MB) plus some integer math, per fragment. Cheap, and it
    replaces the current inHires branch rather than adding to it.
  - The parts that are identical either way — the atlas texture, the
    compute-shader brick upload path, the background loader threads, and the
    focus-distance eviction policy are all unchanged between the two options.
    The choice only affects how the shader finds a chunk.
  - The one real risk I could not test — imageStore into an R8 3D texture on
    Metal needs a live GPU context, which headless Blender refuses. If it fails,
    the fallback is per-Z-slice blits via
    GPUFrameBuffer(color_slots={"texture": atlas, "layer": z}). I'd make this a
    20-minute spike before committing.

  Config lives at the top of bricks.py: BRICK_CORE=64, BRICK_PAD=1,
  SLOTS_PER_AXIS=12 → 1728 slots, 792³ atlas ≈ 497 MB. UPLOADS_PER_DRAW=8,
  LOADER_THREADS=6, FOCUS_RADIUS_CHUNKS=40.

  How it behaves

  Put the 3D cursor where you want detail, run View → Load High-Res Volume. It
  picks the 1728 chunks nearest the cursor that your meshes actually touch,
  queues them on 6 background threads, and each redraw uploads up to 8 and
  re-tags the viewport — so it streams in progressively rather than blocking.
  Everything not resident falls back to L5.

  What I verified vs. what I didn't

  Verified: 27 offline checks (chunk math, padding, eviction, slot packing) and
  8 on-GPU checks — the 497 MB atlas allocates, bricks stream through the
  compute path, and rendered pixels match a CPU trilinear reference to 2.4e-4
  including exactly across chunk boundaries, with the fallback kicking in for
  absent chunks.

  Not verified: the real vesuvius read path. read_brick has only run against a
  stub, so brick reads against the live zarr, threading behaviour with 6
  concurrent Volume handles, and real streaming latency are all untested. That's
  the main thing to watch.

  Two findings worth knowing:

  - Geometry shaders don't exist in Blender's Python GPU API
    (GPUShaderCreateInfo has only vertex/fragment/compute) and Metal has no
    geometry stage at all — hence the page-table approach.
  - GPUTexture has no sub-region upload, so bricks go via a staging texture +
    compute imageStore. That works on Metal; I confirmed it on your machine.

  One caution: I briefly "fixed" a non-existent axis transpose in the lores
  texture based on misread test output, then reverted it once I could read the
  Blender source. ensure_volume now routes through atlas.texture_data(), which
  is a plain C-order pass-through — behaviourally identical to your original
  code. Worth a glance at the L5 render to confirm it looks unchanged.
